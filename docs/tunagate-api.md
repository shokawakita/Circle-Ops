# つなげーと 外部API（イベント作成）メモ

出典: https://tunagate.com/support/external_api
自分がクリエイター（管理人）であるサークルのイベントだけを操作できます。

---

## 認証

リクエストヘッダに `Authorization: Bearer <トークン>` を指定します。
トークンは環境変数 `TUNAGATE_API_TOKEN` に保存します。**発行時の表示は一度きり。**

```
export TUNAGATE_API_TOKEN=tg_xxxxxxxxxxxxxxxxxxxxxxxx
```

> 公式の注意書き:
> トークンは環境変数またはパスワードマネージャーに保存し、
> **コード・チャット・公開リポジトリに直接貼り付けない。**
> 漏洩の恐れがある場合はAPIトークン管理ページからすぐに失効し、新しいトークンを発行する。

---

## 作成は2段階（下書き → 公開）

```
① POST /api/external/events        下書き作成。誰にも見えない状態で保存
         ↓
   （任意）編集画面で人が内容を確認
         ↓
② POST /api/external/events/:id/publish   ここで初めて一般公開
```

誤生成をそのまま公開してしまう事故を防ぐための2段階です。
**このサークルでは、②は必ず人の確認を挟みます**（`CLAUDE.md` の方針）。

## エンドポイント一覧

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/api/external/events` | 下書き作成（`circle_id` 必須） |
| GET | `/api/external/events?circle_id=` | 一覧（`circle_id` 必須。1ページ50件固定・`page` パラメータで移動）。**2026-09-16 確認：下書きが1件も返らない。135件全件 `status: "published"` だった。下書きを含めて取得するには `include_drafts=true` を付ける（2026-09-25 判明。後述）** |
| GET | `/api/external/events/:id` | 詳細。`scripts/tunagate/cli.py show --id <id>` で取得できる（読み取りのみ・公開系フローに影響しない） |
| PATCH | `/api/external/events/:id` | 更新（プランの差し替えは**公開前のみ・全差し替え方式**） |
| POST | `/api/external/events/:id/publish` | 公開（`event_date` と有効なプラン1件以上が必須） |
| DELETE | `/api/external/events/:id` | 削除（他の参加者がいる場合は 422 で拒否） |

---

## 主要パラメータ

| パラメータ | 必須 | 説明 |
|---|---|---|
| `circle_id` | 必須 | 対象サークルID（**create のみ指定**。クリエイター権限を持つサークルのみ） |
| `event[title]` | 必須 | タイトル |
| `event[event_date]` | 公開時必須 | 開催日時 |
| `body` | 任意 | 本文（説明文） |
| `main_image_url` | 任意 | メイン画像のURL。**取得に失敗した場合はリクエスト自体が422で失敗** |
| `events_plans[][...]` | 任意 | プラン配列。**省略時は無料プラン1件が自動生成**（公開には有効なプラン1件以上が必須） |
| `events_plans[][expired_at]` | 任意 | プランの販売期限（早割チケット等に） |

フォームエンコード（`-d "event[title]=..."`）のネスト形式です。

当初は `events_plans[][name]` / `events_plans[][price]`（推定）としていたが、これは誤りで、
実際に送っても無視され、`plan: ""` `creator_price: 0` の空チケットが作成されるだけだった

### 分かっていること・分かっていないこと

- **`capacity`（イベント全体の定員）とチケット定員の合計は、一致しなくてよい。** 実データ（594081）は `capacity: 20` に対しチケット定員合計は `26`（早割系チケットが埋まった後に閉じる設計のため）。このリポジトリの `checks.py` が「チケット定員合計と【定員】の不一致」をエラーにしているのは、この実態と噛み合っていない可能性がある
- どのフィールドが**下書き作成時に必須**で、どれが**公開時のみ必須**かは未確認。今回の 422（「下書き上限に達しています」というメッセージだった）が本当に下書き数によるものか、実は必須フィールド不足が別の形でこのメッセージに丸められているのかは、**実際に送って切り分けるまで分からない**

## curl 実行例

```bash
# 下書き作成
curl -X POST https://tunagate.com/api/external/events \
  -H "Authorization: Bearer $TUNAGATE_API_TOKEN" \
  -d "circle_id=123" \
  -d "event[title]=もくもく会" \
  -d "event[event_date]=2099-01-01T19:00:00"

# 公開（レスポンスの id を使う）
curl -X POST https://tunagate.com/api/external/events/456/publish \
  -H "Authorization: Bearer $TUNAGATE_API_TOKEN"
```

## エラーコード

エラー時のレスポンスボディは常に `{ "error": "メッセージ" }` の形式です。

| ステータス | 意味 |
|---|---|
| 401 | トークンが無効・失効・期限切れ |
| 404 | 権限が無い、またはリソースが存在しない（**権限の有無は区別されない**） |
| 422 | 入力エラー・公開条件未達 など。**下書き上限は2026-09-25に運営側が撤廃済み（後述）。過去にこの422が出ていた場合の原因ではなくなった** |

## 運用上、先に効いてくる制約

| 制約 | 対応 |
|---|---|
| ~~下書きは10件まで~~ | **2026-09-25 運営側が撤廃済み。下書き数にかかわらず作成できる。**（旧問題の詳細は下記「下書き上限エラー」参照。過去の記述は経緯として残す） |
| **`main_image_url` の取得失敗でリクエスト全体が422** | 画像URLは事前に到達確認する。**Notion添付の署名付きURLは数分で失効するため、そのまま渡さない** |
| **プランの差し替えは公開前のみ・全差し替え方式** | 価格や定員を直すなら公開前に。PATCH では配列を丸ごと送る（差分ではない） |
| **プラン省略＝無料プラン1件が自動生成** | 参加費ありの回でプランを渡し忘れると、無料イベントとして公開されうる。**プラン必須チェックを入れる** |
| 404 が権限不足と不在を区別しない | 失敗時に「消えた」と誤判定しない。`circle_id` とトークンの持ち主を先に確認する |
| 一覧は1ページ50件固定 | `page` で回す。デフォルトでは下書きは含まれない。含めるには `include_drafts=true` を付ける（下記参照） |
| 参加者がいると DELETE が422 | 削除は基本使わない。中止は Notion 側のステータスで管理する |
| **一覧APIはデフォルトで下書きを返さない** | `count_drafts()`（`scripts/tunagate/client.py`）は `GET /api/external/events` を数えて下書き数を判定しているが、`include_drafts=true` を付けない限りこのAPIは公開済みイベントしか返さない。**つまり現状の実装は下書きを検知できず、常に過小報告（0件）する。** `include_drafts=true` に対応する改修が必要。改修前は `check --with-draft-count` の結果を鵜呑みにせず、正確な件数はつなげーとの管理画面で確認すること（ただし下書き上限自体は撤廃済みなので、この件数確認はもう「上限超過を避けるため」には必要ない） |

## 下書き上限エラーの原因判明・撤廃（2026-09-25）

サークルID 97956 で `POST /api/external/events` が「未公開の下書きイベントが上限（10件）に達しています」（422）を返す一方、管理画面の下書き一覧には1件しか表示されない、という食い違いについて運営に問い合わせ、回答を得た。

### 問い合わせ内容（要点）

- 最小構成（`circle_id` / `event[title]` / `event[event_date]` のみ）でも同じ422が再現する
- `GET /api/external/events?circle_id=97956` を全ページ取得しても135件全件 `status: "published"` で、下書きは1件も含まれない。このAPIでは下書き件数を確認できない
- 確認したかったこと: 上限のカウント対象は何か／管理画面の「下書き」表示とAPI側のカウント対象は一致するか／現在10件とカウントされている対象をGET系から確認する方法はあるか

### 回答内容（運営チーム）

1. **上限は撤廃済み。** 現在は下書きの件数にかかわらずイベントを作成できる。
2. **カウント対象の実態**: 上限判定は**サークル単位ではなくアカウント単位**で、そのアカウントが持つ**すべてのサークル**の下書きを合算していた。さらに、**開催日が過去のもの**や**タイトルが未入力のまま保存された下書き**も、すべてカウント対象に含まれていた。
3. **管理画面との不一致の理由**: 管理画面の下書き一覧は「タイトルが入力済み」「直近3ヶ月以内に更新」「開催日が未来または未設定」という条件で絞り込んで表示していたのに対し、API側の上限判定にはこれらの条件が無かった。そのため画面上は1件でも、実際のカウント対象は別物だった。
4. 蓄積していた下書きの大半は、**イベント作成画面を開いた際に自動生成される、タイトル未入力の空データ**（作成を途中でやめた際に残るもの）だった。ユーザー操作の問題ではない。
5. **下書きを含めた取得方法**: `GET /api/external/events?circle_id=97956&include_drafts=true` を付けると下書きも含めて取得できる。このパラメータは公式ドキュメントに記載が無く、運営側も「ドキュメントの説明が不足していた」と認めている。
6. 上限は撤廃済みのため、下書きを削除する必要はない。
7. （余談）過去のイベントコピー機能は一時的に利用できない状態だったが、現在は復旧している。

### 今後の対応（未実施・要検討）

- `scripts/tunagate/client.py` の `count_drafts()` / `list_events()` は `include_drafts=true` に未対応。上限撤廃により緊急性は下がったが、下書き件数を正確に把握したい場面（クリーンアップ判断など）のために対応を検討する
- `_explain()` の422ヒント文言（「下書き上限（10件）超過」）は古い情報なので更新が必要
