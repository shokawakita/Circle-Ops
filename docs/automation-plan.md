# イベント作成の自動化プラン（提案）

現状の手作業を工程単位に分解し、「Claude に任せられるもの／人が残すもの」を切り分けたものです。
**実装前の提案段階**。ここで方針を決めてから、スキルとスクリプトを作ります。

前提として置いた方針は1つだけです。

> **品質とやり方は変えない。人がやっている判断は人に残し、転記と下書きだけを機械に渡す。**

そのため、つなげーとへの公開・Googleフォームの送信・SNS投稿など
**外に出る操作は「下書きを作って止まる」までを自動化**し、最後のボタンは必ず人が押します。

## 0. 現状の棚卸し

### すでにできている資産（作り直さない）

Notion 側に、自動化の受け皿がすでにほぼ揃っています。

| DB | 中身 | 自動化での役割 |
|---|---|---|
| `TEST_Event_Projects_DB` | イベント本体。`ep_*` プロパティ群を保持 | **単一の正**。ここを埋めれば他が決まる |
| `Tickets_DB` | チケット（価格・定員・支払方法） | つなげーとのチケット情報の元 |
| `Venues_DB` | 会場（所在地・収容・料金・使用可能時間帯） | 会場候補の提示と原価計算 |
| `Event Costs_DB` | 支出管理（経費精算・イベント別支出） | 開催後の実績入力先 |
| `Participants_DB`（参加者・関係者） | 参加者 | 開催後の参加履歴更新 |

特に大きいのが **`ep_` プレフィックスのプロパティ群**です。
`ep_イベントID`（同期キー）・`ep_連携`（チェックボックス）・`ep_イベントURL` があり、
`Event-Platform` ビューで「未連携かつ進行中」を抽出する形まで出来ています。
つまり **Notion → つなげーと の同期レイヤーは設計済み**で、あとは実際に叩く部分だけが空いています。

### 命名規則（観測した範囲）

- イベント: `YYMM-種別_イベント名`（`ID` インドア / `OD` アウトドア / `FD` フード）
  例 `2610-ID_ボードゲーム会`。**フードがメインなら `FD`**
詳細は `docs/notion-event-rules.md`。

## 3. Notion の使い方のルール

### 3.1 `ep_*` プロパティは使わない

`ep_` プレフィックスのプロパティは、イベントプラットフォームのアプリ作成時に使ったものです。
**現在の運用では使いません。** `TEST_Event_Projects_DB` / `Tickets_DB` / `Venues_DB` すべてで同じ扱いです。

- Claude は `ep_*` を**読まない・書かない**
- 自動化は `ep_*` 以外のプロパティと、ページ本文、リレーション先のDBで組み立てる
- 新しくプロパティを足す場合も `ep_` を付けない

### 3.2 入力ルール

イベント作成のルールは `docs/notion-event-rules.md` にまとめました。要点だけ。

- タイトルは `YYMM-種別_イベント名`
- `開催年度` `開催月` `開催予定期間` `イベントタイプ` は必須入力
- `進捗状況` は つなげーと作成前 `企画・計画中` → 作成後 `進行中`。**`完了` は人が付ける**
- `参加窓口` は つなげーとのURL（作成後に入力）
- `確定申告判定` は つなげーと経由なら「対象」、`優先度` は「中」
- `参加者・関係者` `確定日時` `関連タスク` は記載不要

### 3.3 参加費・定員・募集タイトル・メイン画像はページ本文から読む

プロパティを増やさず、**ページ本文の `## イベント概要` に `【】` 付きのキーワード**で書きます。

理由は2つ。

1. 参加費は早割・通常など**複数のチケット**を設定する予定で、プロパティ管理だと複雑になる
2. `【】` という一意の目印にすることで、**表記ゆれを防げる**

```
## イベント概要

【募集タイトル】横浜ではじめましてのボードゲーム会
【メイン画像】https://example.com/images/2610-boardgame.png
【定員】12

【参加費】
| チケット名 | 価格 | 定員 | 販売期限 |
|---|---|---|---|
| 早割 | 2500 | 5 | 2026-10-05 23:59 |
| 通常 | 3000 | 7 |  |
```

`Tickets_DB` と `Venues_DB` でも `ep_*` は使いません。

## 4. つなげーとAPI連携の設計

API仕様は `docs/tunagate-api.md` に整理しました。

### 4.1 2段階が方針とそのまま噛み合う

APIは **下書き作成 → 公開** の2段階です。これは当初からの方針と一致します。

```
Claude:  POST /api/external/events          → 下書き（誰にも見えない）
人:      つなげーとの編集画面で内容を確認
人の承認後: POST /api/external/events/:id/publish  → 公開
```

**Claude は下書きまで。publish は人の確認後にのみ実行します。**

### 4.2 Notion ↔ API の対応

| API パラメータ | Notion 側の取得元 |
|---|---|
| `circle_id` | `.env` の `TUNAGATE_CIRCLE_ID`（`97956`） |
| `event[title]` | ページ本文の `【募集タイトル】`（`イベント項目` は管理用の名前なので別物） |
| `event[event_date]` | `開催予定期間` の開始 |
| `body` | ページ本文の `## 募集本文` 以下（`brand/voice.md` 準拠、`brand/rules.md` の規約を差し込む） |
| `main_image_url` | ページ本文の `【メイン画像】`。**恒久URLを置く。**Notion添付の署名付きURLは失効するため使わない |
| `events_plans[]` | ページ本文の `【参加費】` の表（チケット名・価格・定員・販売期限） |
| （レスポンスの `id`） | 公開後に `参加窓口` のURLへ含まれる。**同期キー用の新プロパティは不要** |
| （公開URL） | 公開後に `参加窓口` へ書き戻す |
| （作成済みかの判定） | `進捗状況`。`企画・計画中` = 未作成、`進行中` = 作成済み |

### 4.3 同期キー

**下書きの段階でイベントURLが発行される**ため、下書きを作った直後に `参加窓口` へ書き戻せます。
同期キー用の新しいプロパティは不要です。

| `参加窓口` | `進捗状況` | 状態 | 次の操作 |
|---|---|---|---|
| 空 | `企画・計画中` | 未作成 | `POST /api/external/events` で下書き作成 |
| あり | `進行中` | 下書き or 公開済み | `PATCH /api/external/events/:id` で更新 |

イベントIDは `参加窓口` のURLから取り出します。

---

### 4.4 事故を防ぐためのチェック

`docs/tunagate-api.md` の制約から、実装時に必ず入れる検査です。

- **下書きは10件まで。** 作成前に一覧を取得して残り枠を数える（超えると422）
- **プランを省略すると無料プランが自動生成される。** 有料回でプラン未指定なら中断する
- **`main_image_url` の取得失敗はリクエスト全体を422にする。** 事前に到達確認する
- **プランの差し替えは公開前のみ・全差し替え方式。** PATCH では配列を丸ごと送る
- `参加窓口` にURLが入っているイベントは、新規作成ではなく**更新**として扱う（二重作成の防止）
- 404は権限不足と不在を区別しない。「消えた」と誤判定しない
- 失敗したらNotionを書き換えずにそのまま止める（中途半端な同期状態を作らない）

### 4.5 実装の置き場所

```
scripts/tunagate/
├── client.py          API呼び出しの薄いラッパ（認証・エラー処理・下書き枠チェック）
├── field-map.json     Notion プロパティ ↔ APIパラメータ の対応表
└── sync.py            Notion → つなげーと の下書き作成／更新
```

対応表を1枚のJSONに切り出し、仕様変更時はそこだけ直す形にします。

### 4.6 トークンの取り扱い（要対応）

**チャットに貼られたトークンは、この会話の記録に残っています。失効させて再発行してください。**
つなげーとの公式ドキュメントにも「コード・チャット・公開リポジトリに直接貼り付けない。
漏洩の恐れがある場合はすぐに失効し、新しいトークンを発行する」とあります。

リポジトリには入れません。`.gitignore` で `.env` を除外済みで、`.env.example` は値を空にしてあります。

```
# .env（gitignore 済み。手元にだけ置く）
TUNAGATE_API_TOKEN=＜再発行したトークン＞
TUNAGATE_CIRCLE_ID=97956
```

## 6. `/event-repeat` の動作（パターンA）

最初に作るコマンドです。**「前回のボドゲを10/12（日）14時で」**のような一言から始まります。

### 全体の流れ

```
人: 場所取り（予約）
 ↓
人: /event-repeat 「前回のボドゲを10/12 14時で」
 ↓
Claude: ① 元イベント特定 → ② 差分確認 → ③ Notionページ作成
        → ④ 事前チェック → ⑤ つなげーとに下書き作成 → ⑥ Notion書き戻し → ⑦ 告知文
 ↓
人: つなげーとの編集画面で内容確認 → 公開ボタン → Threads投稿
```

### ① 元イベントを特定する

- `TEST_Event_Projects_DB` から、`イベントタイプ` と直近の `開催予定期間` で候補を探す
- 候補が複数あれば一覧で提示し、どれを元にするか確認する
- 元ページの本文（`## イベント概要` / `## 募集本文`）とプロパティを読む

### ② 差分だけ確認する

再作成で変わるのは基本的に**日付と時刻だけ**です。
それ以外に変更があるかを**まとめて1回だけ**聞きます。

- 会場（変わるなら `Venues_DB` から候補を出す）
- 定員 / 参加費（早割の有無、販売期限）
- 募集タイトル

**会場の予約状況は必ず確認します。** 前回の会場・時間帯・利用料金を提示したうえで、
「この会場・時間で予約は取れていますか？」と聞きます。**予約そのものは人の作業**で、
取れていなければそこで止まります。

不明な値は `TODO:` として残し、埋めた体では進めません。

### ③ Notionページを作る

元ページを下敷きに、`TEST_Event_Projects_DB` へ新規ページを作成します。

| 項目 | 入れるもの |
|---|---|
| タイトル | `YYMM-種別_イベント名`（種別は元イベントから継承） |
| `開催年度` `開催月` `開催予定期間` | 新しい日時から（必須） |
| `イベントタイプ` | 元イベントから継承（必須） |
| `会場情報` | `Venues_DB` へのリレーション |
| `進捗状況` | **`企画・計画中`**（まだ つなげーと未作成のため） |
| `確定申告判定` | **`対象`** |
| `優先度` | `中` |
| `参加窓口` | 空（⑥で入れる） |
| `参加者・関係者` `確定日時` `関連タスク` | 入れない |
| 本文 `## イベント概要` | `【募集タイトル】【メイン画像】【定員】【参加費】` を引き継ぎ、日付を差し替え |
| 本文 `## 募集本文` | 元の本文を引き継ぎ、日時・会場を差し替え |

### ④ つなげーとに投げる前のチェック

ここで止めれば事故になりません。1つでも引っかかれば**作成せずに報告**します。

| 検査 | 落ちると何が起きるか |
|---|---|
| 下書きの残り枠（`GET /api/external/events?circle_id=`） | 10件を超えると 422 |
| `【参加費】` の表があるか | **無いと無料プランが自動生成され、有料の回が無料で公開されうる** |
| `【メイン画像】` のURLが到達するか | 取得失敗でリクエスト全体が 422 |
| チケット定員の合計 = `【定員】` | 数が食い違ったまま公開される |
| `## 募集本文` に参加規約とキャンセルポリシーがあるか（`brand/rules.md`） | 規約の抜け |
| NG語が入っていないか（`brand/voice.md`） | 「恋活」「婚活」「出会い」「絶対に」「必ず」 |
| 飲酒を伴う回の対象年齢 | 20歳以上になっているか |

### ⑤ つなげーとに下書きを作る

```
POST /api/external/events
  circle_id            = 97956
  event[title]         = 【募集タイトル】
  event[event_date]    = 開催予定期間の開始
  body                 = ## 募集本文 の内容
  main_image_url       = 【メイン画像】
  events_plans[]       = 【参加費】の表の各行
```

**ここで止まります。公開（`publish`）は叩きません。**
明示的に「公開して」と言われたときだけ実行します。

### ⑥ Notion に書き戻す

- 下書きのURLを `参加窓口` に入れる
- `進捗状況` を `企画・計画中` → **`進行中`** に変える

途中で失敗した場合は Notion を書き換えずに止めます（中途半端な同期状態を作らない）。

### ⑦ 告知文の下書き

`イベントタイプ` が 🍶日本酒 の回は、Threads 用の投稿文を `brand/voice.md` 準拠で作ります。
**投稿は人**が行います。

### 最後に出すもの

- つなげーとの下書きURL
- Notion のページURL
- **人がやること**: ①下書きの内容確認 ②公開ボタン ③（日本酒なら）Threads投稿

### 人に残る作業

| 残る | 消える |
|---|---|
| 場所取り（予約） | つなげーとへの入力 |
| 下書きの内容確認 | Notionへの同じ内容の再入力 |
| 公開ボタン | 規約・キャンセルポリシーの貼り付け |
| Threads投稿 | 告知文の作成 |
