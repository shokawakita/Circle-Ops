# イベント作成の自動化プラン（提案）

現状の手作業を工程単位に分解し、「Claude に任せられるもの／人が残すもの」を切り分けたものです。
**実装前の提案段階**。ここで方針を決めてから、スキルとスクリプトを作ります。

前提として置いた方針は1つだけです。

> **品質とやり方は変えない。人がやっている判断は人に残し、転記と下書きだけを機械に渡す。**

そのため、つなげーとへの公開・Googleフォームの送信・SNS投稿など
**外に出る操作は「下書きを作って止まる」までを自動化**し、最後のボタンは必ず人が押します。

## 0. 現状の棚卸し

### すでにできている資産（作り直さない）

Notion 側に、自動化の受け皿がすでにほぼ揃っています。

| DB | 中身 | 自動化での役割 |
|---|---|---|
| `TEST_Event_Projects_DB` | イベント本体。`ep_*` プロパティ群を保持 | **単一の正**。ここを埋めれば他が決まる |
| `Tickets_DB` | チケット（価格・定員・支払方法） | つなげーとのチケット情報の元 |
| `Venues_DB` | 会場（所在地・収容・料金・使用可能時間帯） | 会場候補の提示と原価計算 |
| `Event Costs_DB` | 支出管理（経費精算・イベント別支出） | 開催後の実績入力先 |
| `Event_Task_DB` | 37個の共通タスク（`01_01_`〜`11_02_`） | 複製してイベント別タスクを生成 |
| `Participants_DB`（参加者・関係者） | 参加者 | 開催後の参加履歴更新 |

特に大きいのが **`ep_` プレフィックスのプロパティ群**です。
`ep_イベントID`（同期キー）・`ep_連携`（チェックボックス）・`ep_イベントURL` があり、
`Event-Platform` ビューで「未連携かつ進行中」を抽出する形まで出来ています。
つまり **Notion → つなげーと の同期レイヤーは設計済み**で、あとは実際に叩く部分だけが空いています。

### 命名規則（観測した範囲）

- イベント: `YYMM-XX_イベント名`（例 `2608-ID_シェアハウスタコスパーティー`、`2508_FD-日本酒会`）
- タスク: `工程番号_連番_タスク名`（例 `01_01_開催時間の検討`）
- 複製元: `9999_ボドゲタスク複製用` / `9999_タスク複製用（ボドゲ以外）` / `991231_複製用イベント`

## 1. パターン別・工程ごとの自動化可否

凡例
🟢 **自動** … Claude が実行。人は結果を確認するだけ
🟡 **下書き** … Claude が完成形を作る。実行ボタンは人が押す
🔴 **人** … 自動化しない（できない／しないほうがよい）

### パターンA: つなげーと_既存イベントの再度作成（月4回・最頻出）

| # | 工程 | 判定 | 自動化後の姿 |
|---|---|---|---|
| 1 | 場所取り | 🔴 人 | 予約は人。ただし **前回の会場・時間帯・料金を Claude が提示**して、確認の手間だけ削る |
| 2 | イベントページ作成（つなげーと） | 🟢 自動 | 前回イベントの `ep_*` を引き継ぎ、日付だけ差し替えて API で作成 |
| 3 | イベントページ作成（Notion） | 🟢 自動 | 過去ページを複製 → 日付・タイトル更新 → `ep_イベントID` / `ep_イベントURL` を書き戻し → `ep_連携` にチェック |
| 3b | （追加）タスク生成 | 🟢 自動 | 37個の共通タスクを `Event_Task_DB` に複製し、イベントへリレーション |
| 4 | 日本酒の場合、告知（threads） | 🟡 下書き | `brand/voice.md` 準拠の投稿文を生成。投稿は人 |

**削減対象**: 工程2・3・3b の転記作業がまるごと消えます。
1回の開催につき、つなげーと入力とNotion入力で**同じ情報を2回打ち込んでいる**のが現状の最大のムダです。

### パターンB: つなげーと_新規イベントの作成

| # | 工程 | 判定 | 自動化後の姿 |
|---|---|---|---|
| 1 | 場所取り | 🔴 人 | `Venues_DB` から条件に合う候補を3件提示（収容・料金・時間帯・エリア） |
| 2 | 予算作成 | 🟡 下書き | 会場費・参加費から**損益分岐人数**まで自動計算。数字の確定は人 |
| 3 | イベントページ作成（つなげーと） | 🟢 自動 | 予算確定後、A と同じ流れ |
| 4 | イベントページ作成（Notion） | 🟢 自動 | 同上 |

新規は「2. 予算作成」が本体なので、ここは**人の判断を残したまま計算だけ肩代わり**します。
`02_01_ラインナップ決め` 〜 `02_04_支出整理` の4タスクのうち、`02_02_想定利益計算` が丸ごと自動になります。

### パターンC: シェアハウス_イベントの作成（協賛金申請用）

| # | 工程 | 判定 | 自動化後の姿 |
|---|---|---|---|
| 1 | 予算作成・参加者調整 | 🟡 下書き | 品目表から合計・1人あたりを自動集計。**協賛金上限（例3万円）に対する残額**も出す |

| 3 | イベントページ作成（Notion） | 🟢 自動 | 既存ページと同じ構成（概要／スケジュール／出席整理／予算／注意点／購入商品／担当割）で作成 |
| 4 | （イベント後）SNS投稿 | 🟡 下書き | 協賛条件に沿った投稿文を生成 |
| 4 | （イベント後）レシート | 🟡 下書き | 写真を渡せば品目・金額を読み取り、`Event Costs_DB` への登録内容を作成 |

> 投稿文の生成時にその条件を満たしているかチェックリストで検証します。

## 3. Notion の使い方のルール

### 3.1 `ep_*` プロパティは使わない

`TEST_Event_Projects_DB` の `ep_` プレフィックスのプロパティは、
**イベントプラットフォームのアプリ作成時に使ったもので、現在の運用では使いません。**

- Claude は `ep_*` を**読まない・書かない**
- 自動化は `ep_*` 以外のプロパティと、ページ本文、リレーション先のDBで組み立てる
- 新しくプロパティを足す場合も `ep_` を付けない

### 3.2 使うプロパティ

| プロパティ | 型 | 自動化での役割 |
|---|---|---|
| `イベント項目` | title | 管理用のイベント名（`YYMM-XX_企画名`） |
| `イベントタイプ` | multi_select | 企画の分類。告知文のトーンと台本の分岐に使う |
| `開催予定期間` | date（時刻あり・範囲） | 開催日時と終了日時 |
| `確定日時` | date | 日程が確定した時点の記録 |
| `会場情報` | relation → `Venues_DB` | 会場。原価と収容人数の元 |
| `場所詳細` | rollup | 会場の所在地 |
| `チケット一覧` | relation → `Tickets_DB` | 参加費と定員 |
| `参加窓口` | url | **つなげーとの公開URL。ここから イベントID も取り出す** |
| `進捗状況` | status | 未着手／企画・計画中／進行中／保留／完了／中止 |
| `詳細` | text | 補足 |
| `開催年度` / `開催月` | select | 集計と絞り込み |
| `確定申告判定` | select | 対象／対象外 |
| `関連タスク` | relation | 37個の共通タスク |
| `参加者・関係者` | relation | 参加者（**ニックネームのみ**） |
| `関連サークル` / `関連資料` / `優先度` | — | そのまま |

**募集本文はプロパティではなくページ本文**に置きます。
既存のシェアハウス回のページ（概要／スケジュール／出席整理／予算／注意点／購入商品／担当割）の構成をそのまま踏襲します。

> `Tickets_DB` と `Venues_DB` にも `ep_*` があります。特に `Tickets_DB` は
> タイトルプロパティ自体が `ep_チケット名` のため、同じルールをそのまま当てられません。

## 4. つなげーとAPI連携の設計

API仕様は `docs/tunagate-api.md` に整理しました。

### 4.1 2段階が方針とそのまま噛み合う

APIは **下書き作成 → 公開** の2段階です。これは当初からの方針と一致します。

```
Claude:  POST /api/external/events          → 下書き（誰にも見えない）
人:      つなげーとの編集画面で内容を確認
人の承認後: POST /api/external/events/:id/publish  → 公開
```

**Claude は下書きまで。publish は人の確認後にのみ実行します。**

### 4.2 Notion ↔ API の対応

| API パラメータ | Notion 側の取得元 |
|---|---|
| `circle_id` | `.env` の `TUNAGATE_CIRCLE_ID`（`97956`） |
| `event[title]` | **TODO: 決める。** `イベント項目` は管理用の名前（`2608-ID_…`）なので、募集用のタイトルの置き場所が要検討 |
| `event[event_date]` | `開催予定期間` の開始 |
| `body` | **ページ本文**から生成（`brand/voice.md` 準拠、`brand/rules.md` の規約を差し込む） |
| `main_image_url` | **TODO: 恒久URLが必要。** Notion添付の署名付きURLは数分で失効するため使えない |
| `events_plans[]` | `チケット一覧` の各行（価格・定員・販売期限） |
| （レスポンスの `id`） | `参加窓口` のURLに含まれるため、**同期キー用の新プロパティは不要** |
| （公開URL） | `参加窓口` に書き戻す |

### 4.3 足りないもの

`ep_*` を使わない場合、**参加費と定員の置き場所**が `TEST_Event_Projects_DB` 側にありません。
3案あります。

| 案 | 内容 | 評価 |
|---|---|---|
| **案1（推奨）** | Events DB に `定員`（number）と `参加費`（number）を新規追加 | 追加2つだけ。`/kpi-monthly` の集計もここから引ける |
| 案2 | `Tickets_DB` を使う | 既存だが、そのDB自体が `ep_*` 中心。ルールの整合が取れない |
| 案3 | ページ本文の「イベント概要」から読む | 追加ゼロだが、表記ゆれで壊れやすい |

### 4.4 事故を防ぐためのチェック

`docs/tunagate-api.md` の制約から、実装時に必ず入れる検査です。

- **下書きは10件まで。** 作成前に一覧を取得して残り枠を数える（超えると422）
- **プランを省略すると無料プランが自動生成される。** 有料回でプラン未指定なら中断する
- **`main_image_url` の取得失敗はリクエスト全体を422にする。** 事前に到達確認する
- **プランの差し替えは公開前のみ・全差し替え方式。** PATCH では配列を丸ごと送る
- `参加窓口` にURLが入っているイベントは、新規作成ではなく**更新**として扱う（二重作成の防止）
- 404は権限不足と不在を区別しない。「消えた」と誤判定しない
- 失敗したらNotionを書き換えずにそのまま止める（中途半端な同期状態を作らない）

### 4.5 実装の置き場所

```
scripts/tunagate/
├── client.py          API呼び出しの薄いラッパ（認証・エラー処理・下書き枠チェック）
├── field-map.json     Notion プロパティ ↔ APIパラメータ の対応表
└── sync.py            Notion → つなげーと の下書き作成／更新
```

対応表を1枚のJSONに切り出し、仕様変更時はそこだけ直す形にします。

### 4.6 トークンの取り扱い（要対応）

**チャットに貼られたトークンは、この会話の記録に残っています。失効させて再発行してください。**
つなげーとの公式ドキュメントにも「コード・チャット・公開リポジトリに直接貼り付けない。
漏洩の恐れがある場合はすぐに失効し、新しいトークンを発行する」とあります。

リポジトリには入れません。`.gitignore` で `.env` を除外済みで、`.env.example` は値を空にしてあります。

```
# .env（gitignore 済み。手元にだけ置く）
TUNAGATE_API_TOKEN=＜再発行したトークン＞
TUNAGATE_CIRCLE_ID=97956
```
