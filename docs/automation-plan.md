# イベント作成の自動化プラン（提案）

現状の手作業を工程単位に分解し、「Claude に任せられるもの／人が残すもの」を切り分けたものです。
**実装前の提案段階**。ここで方針を決めてから、スキルとスクリプトを作ります。

前提として置いた方針は1つだけです。

> **品質とやり方は変えない。人がやっている判断は人に残し、転記と下書きだけを機械に渡す。**

そのため、つなげーとへの公開・Googleフォームの送信・SNS投稿など
**外に出る操作は「下書きを作って止まる」までを自動化**し、最後のボタンは必ず人が押します。

## 0. 現状の棚卸し

### すでにできている資産（作り直さない）

Notion 側に、自動化の受け皿がすでにほぼ揃っています。

| DB | 中身 | 自動化での役割 |
|---|---|---|
| `TEST_Event_Projects_DB` | イベント本体。`ep_*` プロパティ群を保持 | **単一の正**。ここを埋めれば他が決まる |
| `Tickets_DB` | チケット（価格・定員・支払方法） | つなげーとのチケット情報の元 |
| `Venues_DB` | 会場（所在地・収容・料金・使用可能時間帯） | 会場候補の提示と原価計算 |
| `Event Costs_DB` | 支出管理（経費精算・イベント別支出） | 開催後の実績入力先 |
| `Event_Task_DB` | 37個の共通タスク（`01_01_`〜`11_02_`） | 複製してイベント別タスクを生成 |
| `Participants_DB`（参加者・関係者） | 参加者 | 開催後の参加履歴更新 |

特に大きいのが **`ep_` プレフィックスのプロパティ群**です。
`ep_イベントID`（同期キー）・`ep_連携`（チェックボックス）・`ep_イベントURL` があり、
`Event-Platform` ビューで「未連携かつ進行中」を抽出する形まで出来ています。
つまり **Notion → つなげーと の同期レイヤーは設計済み**で、あとは実際に叩く部分だけが空いています。

### 命名規則（観測した範囲）

- イベント: `YYMM-XX_イベント名`（例 `2608-ID_シェアハウスタコスパーティー`、`2508_FD-日本酒会`）
- タスク: `工程番号_連番_タスク名`（例 `01_01_開催時間の検討`）
- 複製元: `9999_ボドゲタスク複製用` / `9999_タスク複製用（ボドゲ以外）` / `991231_複製用イベント`

## 1. パターン別・工程ごとの自動化可否

凡例
🟢 **自動** … Claude が実行。人は結果を確認するだけ
🟡 **下書き** … Claude が完成形を作る。実行ボタンは人が押す
🔴 **人** … 自動化しない（できない／しないほうがよい）

### パターンA: つなげーと_既存イベントの再度作成（月4回・最頻出）

| # | 工程 | 判定 | 自動化後の姿 |
|---|---|---|---|
| 1 | 場所取り | 🔴 人 | 予約は人。ただし **前回の会場・時間帯・料金を Claude が提示**して、確認の手間だけ削る |
| 2 | イベントページ作成（つなげーと） | 🟢 自動 | 前回イベントの `ep_*` を引き継ぎ、日付だけ差し替えて API で作成 |
| 3 | イベントページ作成（Notion） | 🟢 自動 | 過去ページを複製 → 日付・タイトル更新 → `ep_イベントID` / `ep_イベントURL` を書き戻し → `ep_連携` にチェック |
| 3b | （追加）タスク生成 | 🟢 自動 | 37個の共通タスクを `Event_Task_DB` に複製し、イベントへリレーション |
| 4 | 日本酒の場合、告知（threads） | 🟡 下書き | `brand/voice.md` 準拠の投稿文を生成。投稿は人 |

**削減対象**: 工程2・3・3b の転記作業がまるごと消えます。
1回の開催につき、つなげーと入力とNotion入力で**同じ情報を2回打ち込んでいる**のが現状の最大のムダです。

### パターンB: つなげーと_新規イベントの作成

| # | 工程 | 判定 | 自動化後の姿 |
|---|---|---|---|
| 1 | 場所取り | 🔴 人 | `Venues_DB` から条件に合う候補を3件提示（収容・料金・時間帯・エリア） |
| 2 | 予算作成 | 🟡 下書き | 会場費・参加費から**損益分岐人数**まで自動計算。数字の確定は人 |
| 3 | イベントページ作成（つなげーと） | 🟢 自動 | 予算確定後、A と同じ流れ |
| 4 | イベントページ作成（Notion） | 🟢 自動 | 同上 |

新規は「2. 予算作成」が本体なので、ここは**人の判断を残したまま計算だけ肩代わり**します。
`02_01_ラインナップ決め` 〜 `02_04_支出整理` の4タスクのうち、`02_02_想定利益計算` が丸ごと自動になります。

### パターンC: シェアハウス_イベントの作成（協賛金申請用）

| # | 工程 | 判定 | 自動化後の姿 |
|---|---|---|---|
| 1 | 予算作成・参加者調整 | 🟡 下書き | 品目表から合計・1人あたりを自動集計。**協賛金上限（例3万円）に対する残額**も出す |
| 2 | Googleform申請 | 🟡 下書き | 設問に対応した回答文を生成し、**prefill URL**（回答が入った状態のフォームURL）を出力。送信は人 |
| 3 | イベントページ作成（Notion） | 🟢 自動 | 既存ページと同じ構成（概要／スケジュール／出席整理／予算／注意点／購入商品／担当割）で作成 |
| 4 | （イベント後）SNS投稿 | 🟡 下書き | 協賛条件に沿った投稿文を生成 |
| 4 | （イベント後）レシート | 🟡 下書き | 写真を渡せば品目・金額を読み取り、`Event Costs_DB` への登録内容を作成 |
| 4 | （イベント後）参加者メンバー連携 | 🟢 自動 | 出席表から `Participants_DB` を更新（**ニックネームのみ**） |

> 協賛条件（SNS投稿の要件など）は Notion の「ソーシャルデザインの協賛金条件の共有」に整理があるので、
> 投稿文の生成時にその条件を満たしているかチェックリストで検証します。

## 3. つなげーとAPI連携の設計

### 3.1 現状わかっていないこと

このセッションのネットワーク制限により `tunagate.com` に到達できず、
**API仕様（エンドポイント・認証ヘッダ・パラメータ名）を確認できていません。**

進めるには、次のどちらかが必要です。

1. `https://tunagate.com/support/external_api` の内容をチャットに貼っていただく（最短）
2. 環境のネットワークポリシーで `tunagate.com` を許可する

### 3.2 仕様が判明したら

`ep_*` プロパティが API のフィールドとほぼ1対1に見えるため、**対応表を1枚のJSONに切り出す**設計にします。
仕様が変わっても、そのJSONだけ直せば済む形です。

```
scripts/tunagate/
├── client.py          API呼び出しの薄いラッパ（認証・リトライ・レート制限）
├── field-map.json     Notion の ep_* ↔ つなげーとAPI のフィールド対応表
└── sync.py            Notion → つなげーと の作成／更新
```

想定する `ep_*` ↔ API の対応（**仕様確認後に確定**）

| Notion プロパティ | 想定する用途 |
|---|---|
| `ep_イベントID` | 作成後に API から返る ID を書き戻す同期キー |
| `ep_イベントURL` | 公開URL。告知文に差し込む |
| `ep_サークルID` | `97956`（つなげーとのサークルID） |
| `ep_タイトル` / `ep_説明文` / `ep_説明文形式` | 募集ページ本文（`plain` / `markdown`） |
| `ep_開催日時` / `ep_終了日時` / `ep_申込締切日時` | 日時 |
| `ep_都道府県` / `ep_開催場所` / `ep_会場詳細` / `ep_集合場所` | 場所。`*_公開` チェックで公開範囲を制御 |
| `ep_定員数` / `ep_最小催行人数` / `ep_参加費` | 募集条件 |
| `ep_キャンセルポリシー` / `ep_グレースピリオド` | キャンセル規定 |
| `ep_決済方法` | `online` / `onsite` |
| `ep_公開種別` | `public` / `members_only` |
| `ep_自動中止判断時間` / `ep_自動中止チェック済み` | 最小催行人数に届かない場合の自動中止 |
| `ep_連携` | 同期済みフラグ。`Event-Platform` ビューの抽出条件 |

### 3.3 事故を起こさないための約束

- **公開は必ず人の確認後。** Claude は `ep_ステータス = draft` までしか作らない
- `ep_イベントID` があるイベントは新規作成ではなく**更新**として扱う（二重作成の防止）
- API から取得した参加者情報のうち、**本名・連絡先はリポジトリに書かない**（`CLAUDE.md` の絶対ルール1）
- 失敗時はNotionを書き換えず、そのまま止める（中途半端な同期状態を作らない）

### 3.4 トークンの取り扱い（要対応）

**チャットに貼られたトークンは、この会話の記録に残っています。セットアップ後に再発行してください。**

リポジトリには**絶対に入れません**。`.gitignore` で `.env` を除外済みです。

```
# .env（gitignore 済み。手元にだけ置く）
TUNAGATE_API_TOKEN=＜再発行したトークン＞
TUNAGATE_CIRCLE_ID=97956
```

雛形として `.env.example` を用意しました。**値は入れていません。**
