## 2. Notion 側の設計方針

### 2-1. 基本方針

**シート＝DB ではなく、「明細は1本の DB に統合し、シートの違いはビューで表現する」。**
理由: 8枚の明細シートは列構成が9割共通（対象イベント/取引日/金額/支払方法/備考）で、分かれている理由は「Numbers ではシートを跨いだ集計ができない」から。Notion ならビューのグループ集計で代替できる。

### 2-2. TEST_Event_Projects_DB を一切変更しないための構成

TEST_Event_Projects_DB は**イベント情報の管理に特化させ、プロパティを1つも追加しない。** そのために:

1. **リレーションは一方向にする。** Notion のリレーションは作成時に「相手のデータベースに表示する」をオフにできる。収支明細DB 側にだけ `対象イベント` プロパティを持ち、TEST 側には列が増えない。
2. **売上も収支明細DB に入れる。** `会計分類` に「売上」を追加し、イベント単位の売上を1レコードとして登録する。これで売上・経費・仕入が同じテーブルに載り、粗利を1本のビューで出せる。DB名は実態に合わせて **収支明細DB** とする。
3. **粗利は formula + グループ集計で出す。** `損益額` formula を持たせ、`対象イベント` でグループ化した sum を見る（詳細は 4章）。

### 2-3. 作るもの

1. **収支明細DB**（新規・移行の主役）— 全明細シート＋売上シートの統合先
2. **取引先マスタDB**（新規）— 法人番号シートの移行先
3. **経費要素マスタDB**（新規）— 定義シートの移行先。分類ルールの参照元
4. **支出管理ページのビュー構成**（サマリ表の代替）

設置場所は「イベント関連DATA BASE」配下に、TEST_Event_Projects_DB と同じ構成（親ページ1枚 → その中にインラインDB）で置く。支出管理ページには**リンクドビューだけ**を置き、DBの実体は持たせない。

```
イベント関連DATA BASE
├─ イベントプロジェクト管理データベース：Test-Event_Projects_DB  ← 既存・無変更
├─ 収支明細管理データベース：Transactions_DB                      ← 新規
├─ 取引先マスタデータベース：Vendors_DB                            ← 新規
└─ 経費要素マスタデータベース：Expense_Rules_DB                    ← 新規
```

移行しないもの: `〜 - 描画`、`売上 - サマリ`（空）、`【参考】` 系4シート（→ 5-3 でトグル化）。

### 3-1-1. 内訳_食べ物 / 内訳_ドリンク を廃止できる根拠（確認済み）

実データを数えた結果:

| 状態 | 行数 |
|---|---|
| 食べ物・ドリンクの両方に金額あり | **8行** |
| 食べ物のみ | 10行 |
| ドリンクのみ | 7行 |
| 両方0 | 1行 |
| 合計（金額入力のある行） | 26行 |

**結論: 内訳2列は不要にできる。**
`支払分類` を「食べ物」「ドリンク」に分け、1レコード＝1金額にすると、増えるレコードは**両方に金額がある8行が2行に割れる分＝+8件だけ**。その代わり:

- `支払分類` でグループ化すれば、食べ物合計・ドリンク合計が sum で出る（内訳列と同じ情報）
- 「食べ物＋ドリンクの合計」も、`支払分類 in [食べ物, ドリンク]` のフィルタで出る
- 他の分類（消耗品・日本酒など）と金額プロパティが1本に揃うので、**全分類横断の合計が単純な sum で出せる**（内訳列があると sum 対象が分類ごとに変わってしまう）

分割による唯一のデメリットは「1枚のレシートが2レコードに分かれ、レシートとの突合がしにくくなる」こと。これは `レシートID` プロパティで束ねて解消する（同じレシートには同じIDを振り、証憑ファイルは両方のレコードに添付するか、片方に添付してIDで辿る）。

### 3-1-2. 売上と決済手数料の持ち方（`×0.92` の置き換え）

`×0.92` はつなげーとの決済手数料（8%）と確定。収支明細DB では**売上を総額で、手数料を経費で、それぞれ別レコードにする。**

例: あるイベントの売上が 10,000円の場合

| 明細名 | 会計分類 | 支払分類 | 金額 | 損益額 |
|---|---|---|---|---|
| `260104_つなげーと_売上` | 売上 | 売上 | 10,000 | +10,000 |
| `260104_つなげーと_決済手数料` | 経費 | 決済手数料 | 800 | −800 |

こうすると:
- `損益額` の sum が自動的に手取り額（9,200円）になる
- 売上総額も手数料総額も、それぞれ独立に集計できる
- 手数料額は入力補助の formula（`売上金額 × 0.08`）を別途持たせてもよいが、実際の入金額とズレる場合があるため**実額を手入力するのが安全**

### 3-3. 経費要素マスタDB（`Expense_Rules_DB`）

1-2 の表（体育館・決済手数料を含む18件）を1行1レコードで登録。プロパティは `支払分類(title) / 記帳タイミング(select) / 会計分類(select) / 購入場所(select) / 判定(select: 申告対象・申告対象外) / 確認方法(text) / 注意点(text)`。

入力時に「これは経費か仕入か、そもそも対象か」を毎回引きに行くための参照表。**収支明細DB とのリレーションは張らない**（支払分類×購入場所の2軸で1レコードが決まる形なので、リレーション化すると入力が重くなるだけ）。

## 4. 集計を収支明細DB のビューだけで完結させる方法

TEST_Event_Projects_DB に何も足さずに、必要な数字を全て収支明細DB のビューから出す。

### 4-1. イベント別の粗利

| 設定項目 | 値 |
|---|---|
| フィルタ | `対象年度 = 2026年度` かつ `申告区分 = 今年度_申告対象` |
| グループ化 | `対象イベント`（リレーション） |
| 集計 | `損益額` を **Sum** |

→ グループごとの小計＝そのイベントの粗利、ビュー全体の総計＝年度の利益。

`損益額` formula が「売上は +、経費・仕入は −」に符号を振っているので、単純な sum が粗利になる。売上・経費・仕入を別々に見たいときは、同じビューに `金額` の Sum を追加し、サブグループを `会計分類` にする。

> **注意**: Notion のリレーションプロパティでのグループ化がうまく機能しない場合の代替として、`イベントコード`（text、例 `2601-ID_ボードゲーム`）を持たせてそれでグループ化する。移行時にどちらで運用するか動作確認する。

### 4-2. 旧サマリ表の置き換え

| 元のサマリ行 | Notion での出し方 |
|---|---|
| 全量 | フィルタなし・`金額` sum |
| 申告対象外 | `申告区分 = 申告対象外` で絞り、`金額` sum |
| 来年の前払い申告 | `申告区分 = 翌年度_前払い(棚卸)` で絞り、`金額` sum |
| 今年の申告対象合計 | `申告区分 = 今年度_申告対象` で絞り、`金額` sum |
| 各分類のサマリ | `申告区分 = 今年度_申告対象` かつ `対象年度 = 2026年度`、`支払分類` でグループ化・`金額` sum |
| 売上サマリ | `会計分類 = 売上`、`対象月` でグループ化・`金額` sum |
| 食べ物・ドリンク内訳 | `支払分類 in [食べ物, ドリンク]`、`支払分類` でグループ化・`金額` sum |
| 日本酒サマリ（在庫状態 × 用途の4象限） | `支払分類 = 日本酒`、`在庫状態` グループ × `用途` サブグループ、`金額` sum |
| 交通費の月別小計 | `支払分類 = 交通費`、`対象月` でグループ化・`金額` sum |

## 5. 支出管理ページ（出力先）に載せる構成案

DBの実体は「イベント関連DATA BASE」配下に置き、このページには**リンクドビュー**を配置する。

```
支出管理
├─ 冒頭: このページの使い方（3行）＋ 免責（税務判断は税理士に確認）
├─ ① 年度サマリ（収支明細DB のリンクドビュー／支払分類でグループ化・金額sum）
├─ ② イベント別収支（同／対象イベントでグループ化・損益額sum）  ← 4-1
├─ ③ 収支明細DB リンクドビュー群
│   ├─ 全明細（テーブル）
│   ├─ 今年度申告対象（申告区分フィルタ）
│   ├─ 翌年度前払い・棚卸（日本酒の「未」在庫）
│   ├─ 申告対象外（対象外理由でグループ化）
│   ├─ 未入力チェック（証憑確認済み=false または 金額が空）
│   ├─ やよい未記帳（やよい記帳済み=false）
│   └─ 分類別（スペース代／EC／交通費／消耗品／食べ物・ドリンク／日本酒／その他 ＝ 旧シートに相当）
├─ ④ 取引先マスタDB リンクドビュー
├─ ⑤ 経費要素マスタDB リンクドビュー（参照専用）
└─ ⑥ トグル「カード決済の支払日と購入日のズレについて（参考）」  ← 5-3
```

### 5-3. 【参考】シートの扱い

- `【参考】口座照会履歴 - 三十三銀行_2026`: 現状ヘッダーのみでデータなし。**移行しない**。
- `【参考】支払い金額内訳整理 - auPayカードの事業費用整理`: ヘッダーのみでデータなし。**移行しない**。事業/個人の切り分けは `申告区分` と `対象外理由` で表現できる。
- `【参考】Amazon費用計算のための整理` 4枚: 支払日対応表なので、上記トグルに表として貼る。**DB化しない**（毎月固定の対応表であり、レコードとして増えていかないため）。

トグルに載せる内容:

1. **3段構造の説明**: `auPayカード ↔ auかんたん決済 ↔ Amazon`。それぞれの間でタイムラグが発生するため、実際の支払日と購入日に大きな差が出る。
2. **auPayカード（旧）の対応表**: auPay支払日 → 対象支払期間 / auかんたん決済支払日 → Amazon購入期間
3. **三井住友カード（新）の対応表**: 締め日 → 引落日 → 対象購入期間
4. **運用ルール**: 収支明細DB では `取引日 = 実際の購入日`、`引落日 = カード引落日` を分けて持ち、**申告は取引日基準で集計する**。カードの支払日ズレは引落日で追跡するだけで、集計には影響させない。

> **TODO（要確認）**: auPay対応表の「対象支払期間」列は、開始日が終了日より後になっている行がある（例: 2026/2/10支払 ← 2025/12/16〜**2025**/1/15）。支払反映のラグとは別に、年の記載が1行ずつ下がる入力ミスが混入していると見られる。正しくは `2025/12/16〜2026/1/15`、`2026/1/16〜2026/2/15`… の連番だと思われるが、この解釈でよいか確認したい。
