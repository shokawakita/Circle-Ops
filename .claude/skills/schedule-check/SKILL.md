# 土日祝日の空きスケジュール確認

イベント企画のために、自分の土日祝日の空き時間を可視化するコマンドです。
**予定は Notion 側の単一の正を読むだけで、ここでは何も書き込みません。**

## 手順

### 1. 対象期間を決める

今日から3ヶ月先までの日付のうち、**土曜・日曜・日本の祝日**をすべて列挙する。
祝日は自己判断せず、`内閣府の祝日データ`（または `holidays-jp` の API など信頼できる情報源）を
確認して確定する。不確かな祝日を勝手に含めない。

### 2. 稼働時間帯を確認する

「空き」を判定する1日の時間帯（例: 9:00〜21:00）は人によって違うため、
**過去にこのコマンドで確認済みでなければ、最初に1回だけ聞く。**
「何時から何時までを稼働時間として空きを探しますか？」のように聞き、
以降のセッションでは聞いた範囲を使う（推測で決め打ちしない）。

### 3. 予定を集める（Notion MCP）

以下の2つを、手順1の対象期間でフィルタして取得する。**`TEST_Event_Projects_DB` が単一の正**
なのでこちらを優先し、`1Task_DB` は個人の予定として突き合わせる。

| DB | プロパティ | 扱い |
|---|---|---|
| `1Task_DB` | `開始予定日時` | 個人の予定。**時刻まで入っているものだけ**をスケジュールとして扱う（下記参照） |
| `TEST_Event_Projects_DB` | `開催予定期間` | サークルの開催予定。日付範囲として取得 |

`ep_*` プロパティは読まない（`CLAUDE.md` の運用ルール）。

**`1Task_DB` は時刻ありのものだけをスケジュール化する。**
`開始予定日時` は日付だけで登録されているタスク（例: 締切日・チェック項目・思い出しメモ）と、
時刻まで指定された予定が混在している。`date:開始予定日時:is_datetime` が `1`（＝時刻まで入力
されている）の行だけを「明確にスケジュールされた予定」として空き時間の計算に使う。
`is_datetime` が `0`（日付のみ）の行は、スケジュールとして扱わず時間帯を差し引かない。
ただし完全に無視はせず、対象期間中に日付のみのタスクがある日は
「時刻未登録タスクあり（要確認）」として手順6のArtifactと出力に軽く添える
（該当タスクのタイトルに個人名が含まれる場合は `CLAUDE.md` 絶対ルール1に従い出さない）。

### 4. つなげーととNotionの整合性を確認する

`TEST_Event_Projects_DB` の `参加窓口` が `https://tunagate.com/circle/97956/events/<id>` の
形式になっている行（＝つなげーと経由のイベント。身内イベントなど `参加窓口` が Notion ページURLの
行や空欄の行は対象外）について、つなげーと側の実際の開催日時と Notion 側の `開催予定期間` が
一致しているか確認する。

1. `参加窓口` のURLからイベントID（末尾の数値）を取り出す
2. 対象期間内の該当イベントごとに `python3 scripts/tunagate/cli.py show --id <id>` を実行する
   （読み取りのみ・公開系フローに影響しない。`TUNAGATE_API_TOKEN` が必要）
3. レスポンスの `event_date`（開始日時）・`event_end_datetime`（終了日時、あれば）を、
   Notion の `開催予定期間` の開始・終了と突き合わせる
4. ずれている行があれば、日付だけのずれか時刻だけのずれかが分かるように明記し、
   **どちらが正しいかは推測せず、要確認事項として出力する**（`CLAUDE.md` 絶対ルール3に準じる）
5. `cli.py show` がエラーになった場合（トークン未設定・404など）も、
   「つなげーと側と突き合わせ未実施」と明記し、確認できたことにしない

### 5. 空き時間を計算する

対象期間の土日祝日それぞれについて、手順2の稼働時間帯から手順3（時刻ありの予定のみ）で
取得した予定を差し引き、**残った時間帯を時間単位で**出す。予定同士が重なる／稼働時間の
一部だけにかかる場合も正しく差し引く。1日まるごと空いている日は「終日空き」とまとめてよい。

### 6. 出力する

日付が新しい順ではなく、**近い日付から**並べる。祝日には祝日名を添える。

```
## 直近3ヶ月の空き（稼働時間 9:00〜21:00）

### 9月
9/27（土）        終日空き
9/28（日）        13:00〜21:00 空き（9:00〜13:00 は予定あり）

### 10月
10/10（土） 祝日「スポーツの日」  9:00〜15:00 空き
10/11（日）        予定なし。ただし終日「開催予定」（TEST_Event_Projects_DB）と重複

...
```

空き時間が無い日は「空きなし」と明記し、省略しない（存在しないことにしない）。
手順4でつなげーとと Notion にずれが見つかった場合は、この出力の冒頭にも要確認事項として明記する。

### 7. グラフで可視化する（Artifact）

手順6のテキスト表に加えて、**同じ内容を Artifact（HTML）でタイムライン表示する。**
文字だけの表は見づらいため、毎回セットで出す。

- `artifact-design` スキルの指示に従う（`Artifact` ツールで `quickstart` → ページ作成の順）
- 色は `dataviz` スキルのステータスパレット（fixed）を使う。カスタムの色を考案しない
  - 空き＝`good`（緑）／予定あり＝`critical`（赤）／時刻未登録で要確認＝`warning`（黄）
  - 同時刻に重複登録がある日は、`critical` の斜線パターンで区別する
- 1日＝1行、9:00〜21:00（手順2で確認した稼働時間帯）を30分刻みのセルで横に並べる
  ライトモード／ダークモードの両方に対応させる（`artifact-design` の指示どおり）
- 各行の下に、予定の時間帯とタイトルをテキストでも添える（ホバーに依存しない）
- 上部に、重複登録・つなげーととのずれなどの要確認事項があれば警告として出す
- 生成したら Artifact のURLを最後に提示する

## 守ること

- Notion に何も書き込まない（読み取り専用のコマンド）
- 祝日を推測で決めない。信頼できる祝日データで確認する
- 稼働時間帯を勝手に決めない。未確認なら毎回聞く
- 個人情報（予定のタイトルに個人名などが含まれる場合）は出力に含めず、
  「予定あり」とだけ表示する（`CLAUDE.md` 絶対ルール1に準じる）
- 金額・日付・人数を勝手に確定しない、と同様に、空き時間も推測で埋めない。
  取得できなかった予定があれば「取得できていない予定がある可能性」を明記する
- `1Task_DB` は日付のみのタスクを予定として扱わない（手順3）。時刻が無いものを
  「一瞬の予定」として空き時間から差し引かない
- つなげーと経由のイベントは、つなげーとAPI側の日時と Notion の食い違いを勝手にどちらかへ
  寄せない（手順4）。ずれが見つかったら要確認事項として出すだけにとどめる

## つまずきやすいところ

| 症状 | 原因 |
|---|---|
| 空き日が実際より少なく出る | `1Task_DB` の日付のみタスク（時刻未登録）を予定として時間帯を差し引いてしまっている。`date:開始予定日時:is_datetime` が `0` の行はスケジュールとして扱わない |
| 空き日が実際より多く出る | `1Task_DB` 側の終了日時が無いタスクを「開始時刻だけの一瞬の予定」として扱ってしまっている。終了日時が無い予定は前後にバッファを持たせるか、ユーザーに確認する |
| 祝日が漏れる／間違う | 祝日データを確認せず土日だけで計算している |
| 稼働時間帯がセッションごとに変わる | 手順2で聞かずに毎回デフォルト値を使い回している。前回と違う範囲を使うときは必ず確認する |
| つなげーととNotionのずれに気づかない | 手順4を省略している、または `参加窓口` がつなげーとURLの行だけに絞らず全行チェックしようとして失敗している |
| `cli.py show` が失敗する | `.env` に `TUNAGATE_API_TOKEN` が無い、またはイベントIDの抽出を誤っている。失敗時は「突き合わせ未実施」と明記し、確認済みと偽らない |
